Chapter 9 · the final practice

Build it from zero

Now build the whole travel API yourself, from an empty folder, in VS Code. Phase by phase. Don't copy from the earlier chapters — go back to them only when you're stuck.

How to use this page
  • Do one phase at a time. Test before you move on — a bug is easy to find when you only changed a little.
  • Every phase has a “Done when” check. Tick the boxes (they're saved).
  • Hints point you back to the right chapter instead of giving code.
  • When it all works, do it a second time, faster. The second time is when it really sticks.

Phase 0 — Set up the project

Goal: an empty project with everything installed.

  • New folder travel-api, opened in VS Code
  • npm init -y
  • npm install express mysql2 dotenv bcrypt cookie-parser
  • Folders: routes, controllers, utils
  • .gitignore with node_modules and .env
  • .env with HOSTNAME, PORT, DB_USER, DB_PASSWORD, DB_NAME — and .env.example with fake values
  • The database exists in Workbench (CREATE DATABASE travel_db;)

You should end up with this shape (files get filled in the next phases):

travel-api/ ├── .env .env.example .gitignore package.json ├── server.js ├── index.js ├── db.js ├── utils/validators.js ├── routes/ userRoutes.js authRoutes.js tripRoutes.js └── controllers/ userController.js authController.js tripController.js

Phase 1 — The app skeleton

Goal: a running server with one test route.

  • index.js: create the app, express.json(), cookieParser(), export { app }
  • A temporary route in index.js: GET /health → { status: 'ok' }
  • server.js: require the app, dotenv.config(), app.listen(process.env.PORT, process.env.HOSTNAME, …)
  • Done when: node server.js prints the URL and http://localhost:5000/health shows {"status":"ok"} in the browser
Stuck?
Chapter 3 (first server) and Chapter 4 (index.js vs server.js).

Phase 2 — The database

Goal: the tables are created automatically when the server starts.

  • db.js: dotenv.config() FIRST, then createPool with the values from process.env
  • db.js: the three CREATE TABLE IF NOT EXISTS strings (USERS, TRIPS, REVIEWS), exported with db
  • server.js: an async function startServer() that awaits the three queries (USERS, TRIPS, then REVIEWS), then calls listen; catch prints the error
  • Done when: the terminal prints the three “table created” lines, and Workbench shows the 3 tables (refresh the Schemas panel)
  • Added a few trips in Workbench with INSERT INTO TRIPS … to test with
Stuck?
Chapter 5 (db.js, server.js, the connection errors list), Chapter 6 (CREATE TABLE), Chapter 8 (REVIEWS table and the order).

Phase 4 — Validation and auth

  • utils/validators.js: sanitizeInput, isValidEmail, isStrongPassword, validateRequired, validateEmail, validatePassword
  • authController.js: registerUser (6 steps) and loginUser
  • authRoutes.js: POST /register, POST /login; mounted at /auth
  • createUser in the users controller also validates and hashes
  • Done when: you can register, see a $2b$… hash in Workbench, log in (200), and fail to log in with a wrong password (401). Registering the same email twice gives 409.

Phase 9 — Clean-up checklist

Teachers check these things. Go through your code one last time:

  • Every early res.status(...) has a return in front of it
  • Every await db.query is inside a try with a 500 in the catch
  • Every catch has console.error(error) so you can debug
  • No ${} inside SQL strings with user values — only ?
  • Fixed routes are above /:id in every router
  • The password (or its hash) never appears in a response
  • The same response shape everywhere (e.g. message + data)
  • No leftover test routes or random console.logs
  • .env is NOT uploaded; .env.example IS
  • A short README.md: how to install (npm install), set up .env, and run (node server.js)
