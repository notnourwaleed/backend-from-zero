The lecture project

The lecture project, file by file

This is the exact travel API from the lectures (the final week 8 version). Here every file is written once, in its finished form, in the order you would build it. No jumping back to change old files.

Why the lectures felt confusing

In class the project grew: the same file was opened again and again over many weeks (db.js changed 4 times, index.js 4 times, server.js 5 times). That's how real projects grow — but when you're learning, it's hard to know which version is the “real” one. On this page there's only one version of each file: the final one.

How to use this page

  • Go top to bottom. Each step is one file (or a group of very similar small files).
  • Long files are cut into parts. The parts, one after another, are the whole file — type them into the same file in that order.
  • After each file there's a ✔ Check: a command that proves the file works before you move on.
  • Every part links to the chapter that explains the idea in depth. If something feels like magic, go read that chapter.
  • Boxes marked “Different from the lecture” show the few places where the lecture code had a bug. The fixed version is used here, and the box tells you what was wrong — so you can compare it with your notes.

If you want to see it working first, jump to the playground at the end: the whole finished project runs there, and you can send it requests.

Why this order?

We build from the bottom up: first the files that don't need any other file of ours (db.js, validators), then the files that use them (controllers), then the files that use those (routes), and last the ones that tie everything together (index.js, server.js). That way, every file you write only uses things that already exist — you never write a require for a file that isn't there yet.

Step 2 — db.js: the connection and the tables

Chapter links: 5. Connecting to MySQL, 6. CREATE TABLE, 8. Foreign keys

This file has one job: give the rest of the project a connection to the database (db), and the SQL text to create the three tables. It doesn't create them itself — server.js will run them at start-up.

Part 1 of 3 — connect

db.js
const mysql = require("mysql2/promise");
const dotenv = require("dotenv");
dotenv.config();

const db = mysql.createPool({
    host: "localhost",
    port: 3306,
    user: process.env.DB_USER,
    password: process.env.DB_PASSWORD,
    database: process.env.DB_NAME
}); // configs
  • mysql2/promise — the version of mysql2 that works with await.
  • dotenv.config() loads .env into process.env. It must come before createPool (why).
  • createPool — a set of ready connections. The rest of the project only ever uses db.query(...).

Part 2 of 3 — the three tables

// Create User Table
const createUserTable = `CREATE TABLE IF NOT EXISTS USERS (
        ID INT AUTO_INCREMENT PRIMARY KEY,
        USERNAME VARCHAR(255) NOT NULL,
        EMAIL VARCHAR(255) UNIQUE NOT NULL,
        PASSWORD VARCHAR(255) NOT NULL,
        ROLE ENUM('admin', 'user') NOT NULL DEFAULT 'user',
        MANAGER_ID INT NULL,
        FOREIGN KEY (MANAGER_ID) REFERENCES USERS(ID)
    );
`;

const createTripTable = `CREATE TABLE IF NOT EXISTS TRIPS (
        ID INT AUTO_INCREMENT PRIMARY KEY,
        DESTINATION VARCHAR(150) NOT NULL,
        COUNTRY VARCHAR(150) NOT NULL,
        COST DECIMAL(10,2) NOT NULL
)`;

const createReviewTable = `CREATE TABLE IF NOT EXISTS REVIEWS (
        ID INT AUTO_INCREMENT PRIMARY KEY,
        USER_ID INT NOT NULL,
        TRIP_ID INT NOT NULL,
        RATING INT NOT NULL CHECK (RATING BETWEEN 1 AND 5),
        FOREIGN KEY (USER_ID) REFERENCES USERS(ID),
        FOREIGN KEY (TRIP_ID) REFERENCES TRIPS(ID),
        UNIQUE (USER_ID, TRIP_ID)
)`;
  • These are just strings (text in backticks) holding SQL. Nothing runs yet.
  • USERS: EMAIL UNIQUE = one account per email. ROLE can only be admin or user. MANAGER_ID points at another user (the boss) — it can be empty (NULL).
  • TRIPS: simple table, DECIMAL(10,2) for money.
  • REVIEWS: connects users and trips. Rating must be 1–5; one review per user per trip.

Step 3 — utils/validators.js: checking input

Chapter link: 7. Validate and sanitize

Six small helper functions. Each returns an error message or null (= OK), except the first three which clean or answer true/false.

Part 1 of 2 — the basic helpers

utils/validators.js
const sanitizeInput = (value) => {
    if (typeof value !== 'string') return '';
    return value.trim().toLowerCase();
};

const isValidEmail = (email) => {
    const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
    return typeof email === 'string' && emailRegex.test(email);
};

const isStrongPassword = (password) => {
    if (typeof password !== 'string') return false;

    const passRegex = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[\W_]).{8,}$/;
    return passRegex.test(password);
};
  • sanitizeInput: " Sara@Mail.com " → "sara@mail.com". Anything that isn't text becomes ''.
  • isValidEmail: “something@something.something”.
  • isStrongPassword: lowercase + uppercase + digit + special character + at least 8 long. (regex explained)

Part 2 of 2 — the validators that return messages

const validateRequired = (fields, requiredKeys) => {
    for (const key of requiredKeys) {
        if (typeof fields[key] !== 'string' ||
            !fields[key].trim()) {
            return `${key} is required`;
        }
    }
    return null;
};

const validateEmail = (email) => {
    if (!email) return 'Email is required';
    if (!isValidEmail(email)) return 'Invalid email format';
    return null;
};

const validatePassword = (password) => {
    if (!password) return 'Password is required';
    if (!isStrongPassword(password)) {
        return 'Password must have 8+ chars, upper, lower, number, and special char';
    }
    return null;
};

module.exports = {
    sanitizeInput,
    isValidEmail,
    isStrongPassword,
    validateRequired,
    validateEmail,
    validatePassword
};

Part 2 of 3 — registerUser (6 steps)

const registerUser = async (req, res) => {
    const { username, email, password } = req.body;

    // 1. Clean input
    const cleanUsername = sanitizeInput(username);
    const cleanEmail = sanitizeInput(email);

    // Do NOT trim or lowercase passwords
    const cleanPassword = password;

    // 2. Check required fields
    const requiredError = validateRequired(
        {
            username: cleanUsername,
            email: cleanEmail,
            password: cleanPassword
        },
        ['username', 'email', 'password']
    );

    if (requiredError) {
        return res.status(400).json({
            message: requiredError
        });
    }

    // 3. Validate email
    const emailError = validateEmail(cleanEmail);

    if (emailError) {
        return res.status(400).json({
            message: emailError
        });
    }

    // 4. Validate password
    const passwordError = validatePassword(cleanPassword);

    if (passwordError) {
        return res.status(400).json({
            message: passwordError
        });
    }

    // 5. Hash password using bcrypt
    try {
        const hashedPassword = await bcrypt.hash(cleanPassword, 12);

        // 6. Parameterized query
        const query = `
            INSERT INTO USERS (USERNAME, EMAIL, PASSWORD, ROLE)
            VALUES (?, ?, ?, ?)
        `;

        const [result] = await db.query(query, [
            cleanUsername,
            cleanEmail,
            hashedPassword,
            'user'
        ]);

        return res.status(201).json({
            message: 'User registered successfully'
        });

    } catch (error) {
        if (error.code === 'ER_DUP_ENTRY') {
            return res.status(409).json({
                message: 'Email already exists'
            });
        }

        return res.status(500).json({
            message: 'Registration error'
        });
    }
};
  • Steps 1–4 check the input. Each problem → return res.status(400) and the function stops.
  • Step 5 hashes the password (never store it as plain text).
  • Step 6 saves with ? placeholders. New users are always 'user', never admin.
  • If the email exists, MySQL refuses because of UNIQUE and throws ER_DUP_ENTRY → we answer 409.

Part 3 of 3 — loginUser + export

const loginUser = async (req, res) => {
    const { email, password } = req.body;

    const cleanEmail = sanitizeInput(email);

    if (!cleanEmail || !password) {
        return res.status(400).json({
            message: 'Please provide both email and password.'
        });
    }

    // Parameterized query prevents SQL injection
    const query = `
        SELECT * FROM USERS WHERE EMAIL = ?
    `;

    try {
        const [users] = await db.query(query, [
            cleanEmail
        ]);

        if (users.length === 0) {
            return res.status(401).json({
                message: 'Invalid email or password.'
            });
        }

        const user = users[0];

        // Compare entered password with stored hash
        const isMatch = await bcrypt.compare(
            password,
            user.PASSWORD
        );

        if (!isMatch) {
            return res.status(401).json({
                message: 'Invalid email or password.'
            });
        }

        return res.status(200).json({
            message: 'User logged in successfully',
            user: {
                id: user.ID,
                username: user.USERNAME,
                email: user.EMAIL,
                role: user.ROLE
            }
        });

    } catch (error) {
        return res.status(500).json({
            message: 'Login error'
        });
    }
};

module.exports = {
    registerUser,
    loginUser
};
  • Find the user by email → none: 401. Compare the password with the hash → no match: 401. Same message both times on purpose (why).
  • The response builds a new object with only safe fields — the password hash is not sent.

Part 4 of 6 — updateUserById (partial update)

// Update a specific user by ID partial update
const updateUserById = async (req, res) => {
    const id = Number(req.params.id);
    const { username, email, password, role } = req.body;

    if (!username && !email && !password && !role) {
        return res.status(400).json({
            message: "Please provide at least one field to update."
        });
    }

    try {
        const selectQuery = `SELECT * FROM USERS WHERE ID = ?`;
        const [users] = await db.query(selectQuery, [id]);

        if (users.length === 0) {
            return res.status(404).json({
                message: "User not found"
            });
        }

        const updatedUsername = username || users[0].USERNAME;
        const updatedEmail = email || users[0].EMAIL;
        const updatedPassword = password ? await bcrypt.hash(password, 12) : users[0].PASSWORD;
        const updatedRole = role || users[0].ROLE;

        const query = `
            UPDATE USERS
            SET USERNAME = ?,
                EMAIL = ?,
                PASSWORD = ?,
                ROLE = ?
            WHERE ID = ?
        `;

        const [result] = await db.query(query, [
            updatedUsername,
            updatedEmail,
            updatedPassword,
            updatedRole,
            id
        ]);

        if (result.affectedRows === 0) {
            return res.status(404).json({
                message: "User not found"
            });
        }

        const updatedUserQuery = `SELECT * FROM USERS WHERE ID = ?`;
        const [updatedUser] = await db.query(updatedUserQuery, [id]);

        return res.status(200).json({
            message: "User updated successfully",
            data: updatedUser
        });

    } catch (error) {
        return res.status(500).json({
            message: "Database error",
        });
    }
};
  1. Nothing sent at all → 400.
  2. Read the current user. Not found → 404.
  3. For each field: the new value if one was sent, otherwise the old one (new || old — Chapter 1).
  4. Save all four with ? placeholders, then read the row again and return it.
Different from the lecture (3 fixes)
  • The lecture builds the UPDATE with '${updatedUsername}' etc. — that's open to SQL injection (anyone can make themselves admin — try it in Practice 7.4), and a name like o'brien crashes it. Here: ? placeholders.
  • The lecture saves a new password as plain text. Here it's hashed with bcrypt, like everywhere else — otherwise that user could never log in again.
  • The lecture runs the first SELECT outside try, so a database error there crashes the request. Here everything is inside try.

Part 2 of 4 — retrieveTripById (sets the cookie)

const retrieveTripById = async (req, res) => {
    const id = Number(req.params.id);

    if (!Number.isSafeInteger(id) || id <= 0) {
        return res.status(400).json({
            message: "Invalid trip ID"
        });
    }

    try {
        const query = "SELECT * FROM TRIPS WHERE ID = ?";
        const [trips] = await db.query(query, [id]);

        if (trips.length === 0) {
            return res.status(404).json({
                message: "Trip not found"
            });
        }

        // Remember the last viewed trip
        res.cookie('lastViewedTrip', String(id), {
            maxAge: 24 * 60 * 60 * 1000, // 1 day
            httpOnly: true,
            secure: true,
            sameSite: 'lax'
        });

        return res.status(200).json({
            data: trips[0]
        });

    } catch (error) {
        return res.status(500).json({
            error: error.message,
            message: "Database error"
        });
    }
};
  • Validate the id → 400. Find the trip → 404. Then set a cookie with the id and return the trip.
  • The cookie is text, so String(id). maxAge is in milliseconds: this is 1 day (the lecture comment says “1 ho”, but the number is a day — see 8.7).

Step 7 — the three routes files

Routes files are short: import the controller functions, connect each to a method + path, export the router. Remember the rule: fixed paths above /:id.

routes/authRoutes.js
const express = require('express');
const {
    registerUser,
    loginUser
} = require('../controllers/authController');

const authRouter = express.Router();

Different from the lecture

In the week 8 lecture, /managers comes after /:id, and in trips, /:id was added at the top — above /last-viewed, /reviews and /ratings. (In week 7 the trips routes worked, because /:id didn't exist yet!) Express takes the first match, so /trips/reviews went to retrieveTripById with id = "reviews" → “Invalid trip ID”. Moving /:id to the bottom fixes all of them. (Chapter 4)

Step 9 — server.js: create the tables, then start

Chapter link: 5. server.js

server.js
const { app } = require('./index.js');
const {
  db,
  createUserTable,
  createTripTable,
  createReviewTable } = require('./db.js');
const dotenv = require('dotenv');
dotenv.config();

async function startServer() {
  try {
    await db.query(createUserTable);
    console.log('Users table created or already exists.');

    await db.query(createTripTable);
    console.log('Trips table created or already exists.');

    await db.query(createReviewTable);
    console.log('Reviews table created or already exists.');

    app.listen(process.env.PORT, process.env.HOSTNAME, () => {
      console.log(`Server is running at http://${process.env.HOSTNAME}:${process.env.PORT}`);
    });
  } catch (error) {
    console.error('Error initializing the database:', error);
    process.exitCode = 1;
    await db.end();
  }
}

startServer();
  • The tables are created in order: REVIEWS points at USERS and TRIPS, so those must exist first.
  • IF NOT EXISTS makes this safe to run every time you start.
  • Only when all tables are ready does the server start listening.
