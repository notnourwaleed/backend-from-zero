Security & login

Your server is open to the whole internet, and some people will try to break it. Four habits protect you from most attacks. Then you'll build register and login.

The four rules

  1. Never upload secrets. Passwords and keys go in .env, and .env goes in .gitignore.
  2. Never trust input. Check (validate) and clean (sanitize) everything the client sends.
  3. Never glue input into SQL. Always use ? placeholders.
  4. Never store plain passwords. Hash them with bcrypt.

Rule 1: .env (and the order mistake)

You met .env in Chapter 5. One mistake is very common: dotenv.config() must run before you use process.env. Before that line runs, the values are all undefined.

Rule 2: validate and sanitize

Validate = check that the data is acceptable (present, right format). If not → 400.
Sanitize = clean it up (remove spaces around it, make email lowercase), so " Sara@Mail.com " and "sara@mail.com" are treated as the same.

The course puts these helpers in utils/validators.js, so every controller can reuse them.

Checking formats with regular expressions

A regular expression (regex) is a pattern for text. You don't need to write them from scratch — but you should be able to read the two from the course:

const emailRegex = /^[^\s@]+@[^\s@]+\.[^\s@]+$/;
emailRegex.test('sara@mail.com');  // true
emailRegex.test('sara@mail');      // false
PieceMeaning
^ … $from the very start to the very end
[^\s@]+one or more characters that are NOT a space and NOT @
@, \.a real @, a real dot

So: “something, @, something, dot, something”.

const passRegex = /^(?=.*[a-z])(?=.*[A-Z])(?=.*\d)(?=.*[\W_]).{8,}$/;
PieceMeaning
(?=.*[a-z])somewhere there's a lowercase letter
(?=.*[A-Z])…an uppercase letter
(?=.*\d)…a digit
(?=.*[\W_])…a special character (like ! or _)
.{8,}at least 8 characters in total

Rule 3: SQL injection

If you build SQL by gluing text together, the user's text becomes part of your SQL command. A clever user can then write SQL instead of a name.

// The code:
const query = `UPDATE USERS SET USERNAME = '${newUsername}' WHERE ID = ${id}`;

// A normal user sends: omar2
//   UPDATE USERS SET USERNAME = 'omar2' WHERE ID = 2                       ✓ fine

// An attacker sends:  hacker', ROLE = 'admin
//   UPDATE USERS SET USERNAME = 'hacker', ROLE = 'admin' WHERE ID = 2      ✗ now they're admin!

The quote ' in their text closed your string, and everything after it is SQL. With a placeholder, MySQL knows the value is only data — quotes and all:

await db.query('UPDATE USERS SET USERNAME = ? WHERE ID = ?', [newUsername, id]);
// the username becomes literally:  hacker', ROLE = 'admin   — harmless text

Rule 4: hash passwords with bcrypt

If your database is ever stolen, plain passwords would let the thief log in as everyone — and on other websites too, since people reuse passwords.

A smoothie

Hashing is like a blender: you can turn fruit into a smoothie, but never turn the smoothie back into fruit. bcrypt turns Hello123! into something like $2b$12$Kq3h…. To check a login, you blend the typed password the same way and compare the smoothies.

npm install bcrypt
const bcrypt = require('bcrypt');

// Register: hash before saving (12 = "salt rounds": how much work. Higher = slower = safer)
const hashedPassword = await bcrypt.hash(password, 12);
// save hashedPassword in the PASSWORD column

// Login: compare the typed password with the saved hash
const isMatch = await bcrypt.compare(typedPassword, user.PASSWORD);  // true or false
  • Hashing the same password twice gives different results (bcrypt adds random “salt”). That's why you can't compare with === — always use bcrypt.compare.
  • Both are async → await.
  • Don't trim() or lowercase passwords — spaces and capitals are part of the password.
  • Never send the PASSWORD column back to the client, not even the hash. Select only the columns you need.
Playground note

The playground uses a fake bcrypt with the same functions, so your code works the same way. The real bcrypt is slower on purpose.

Build register

Register is a recipe of 6 steps. The course writes them as numbered comments — do the same in your project:

  1. Clean the input (sanitize username and email — not the password).
  2. Check required fields → 400.
  3. Validate email → 400.
  4. Validate password → 400.
  5. Hash the password.
  6. INSERT with placeholders → 201. If MySQL says the email already exists (error.code === 'ER_DUP_ENTRY', thanks to UNIQUE) → 409.

Build login

  1. Clean the email. If email or password is missing → 400.
  2. SELECT * FROM USERS WHERE EMAIL = ?. No user → 401.
  3. bcrypt.compare(password, user.PASSWORD). No match → 401.
  4. → 200 with the user's id, username, email, role (not the password).
Why the same message for both 401s?

Answer “Invalid email or password.” in both cases. If you said “email not found”, an attacker could find out who has an account.

What login does NOT do (yet)

Right now, login only checks the password. The server doesn't “remember” you for the next request — every request is a stranger. Remembering logged-in users needs sessions or tokens (like JWT), which usually come later in a course. Cookies (Chapter 8) are the first step.
